## Free-plan backup and restore posture

The provider reports no physical backups and PITR disabled for this Free
project. Supabase recommends regular logical exports for Free projects. Before
representative or migrated data is loaded, the operator must select an approved
encrypted backup destination and perform a logical backup/restore rehearsal.

The intended manual procedure is:

1. Obtain the migration connection from the secret store without printing it.
2. Run role, schema, and data-only logical exports using the current Supabase
   CLI or matching `pg_dump` tooling.
3. Encrypt the export at rest and store it only in the approved Australian
   destination.
4. Record its timestamp, tool/Postgres versions, checksum, retention, and owner.
5. Restore into an empty non-production target and run integrity checks before
   treating the backup as usable.

No representative data exists in the project, so no data backup was created in
Stage 3. The amended contract permits the operator-managed encrypted logical
backup control on Free; Release must set its ongoing cadence and retention and
must not describe it as managed backup or PITR coverage.

## Current Supabase compatibility findings

The current breaking-change scan identified the 2026 change that makes new
Data API table grants explicit rather than automatic. This architecture does
not depend on the Data API and will use a private schema. Any future exception
must separately address grants and RLS; RLS alone does not control whether an
object is reachable through an exposed schema.
